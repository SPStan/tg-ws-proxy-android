# TG WS Proxy Android

Локальный MTProto-прокси для Telegram. Приложение использует интерфейс Kotlin/Compose и нативный движок Rust от [amurcanov](https://github.com/amurcanov/tg-ws-proxy-android). Адрес по умолчанию — `127.0.0.1:1443`. Идентификатор приложения — `com.spstan.tgwsproxy`.

## Установка и подключение Telegram

1. Скачайте `arm64-debug` из успешного запуска [GitHub Actions](https://github.com/SPStan/tg-ws-proxy-android/actions/workflows/android.yml). В архиве находятся APK и файл SHA-256. В командной строке распакованного каталога проверьте `sha256sum -c app-arm64-debug.apk.sha256`. В PowerShell используйте `Get-FileHash -Algorithm SHA256 .\app-arm64-debug.apk`.
2. Если установлен исходный Android-форк, остановите в нём прокси, чтобы освободить порт 1443. Обе версии приложения могут одновременно оставаться установленными.
3. Установите APK. Для установки по USB включите отладку, подтвердите разрешение на телефоне и выполните `adb install -r app-arm64-debug.apk`. Ожидаемый ответ — `Success`.
4. Откройте приложение и разрешите уведомления. Нажмите кнопку с логотипом Telegram. Дождитесь состояния «Подключено» и уведомления фонового сервиса.
5. Нажмите «Применить в Telegram», подтвердите добавление прокси в клиенте и дождитесь статуса его подключения. При изменении домена Fake TLS повторно примените ссылку после перезапуска сервиса.

## Транспорт

| Маршрут | Переключатель выключен | Переключатель включён |
| --- | --- | --- |
| CF-прокси | WSS, 443 | WS, 80 |
| CF Worker | WSS, 443 | WS, 80 |
| Прямое соединение с Telegram | WSS или резервный TCP, 443 | WSS или резервный TCP, 443 |
| HTTP/2 для CF-медиа | TLS с ALPN `h2`, когда включена настройка HTTP/2 | Медиа через доступный WebSocket-маршрут |

При чистой установке переключатель «Выключить TLS для CF-прокси и CF-worker» выключен. Выбор сохраняется. После изменения остановите и запустите прокси или используйте «Перезапуск» в уведомлении. Новый сеанс создаёт новый пул соединений. В журнале появится `CF WebSocket transport: WSS :443` или `CF WebSocket transport: WS :80`.

В режиме WS сетевому посреднику видны заголовки WebSocket, а CF-сервер должен принимать HTTP Upgrade на порту 80. Перенаправление на HTTPS отображается в журнале как `server redirects to HTTPS`. При ошибке WSS прокси может попробовать другой настроенный маршрут. CF-подключения этого сеанса продолжают использовать WSS.

Для CF-прокси и Worker можно указать отдельные списки доменов в настройках. Нажмите «Сохранить параметры транспорта». Пустой список доменов CF-прокси возвращает встроенный список и фоновое обновление. Для входящего Fake TLS укажите маскирующий домен. Ссылка для Telegram будет использовать секрет с префиксом `ee`. Эта настройка применяется на стороне локального сервера независимо от TLS исходящих соединений с CF. В экспериментальном режиме доступны размер буфера сокета, принудительные тестовые DC и входящий PROXY protocol v1 для запуска за доверенным промежуточным сервером.

## Сборка из чистой копии

Для Linux и GitHub Actions используются JDK 17, Gradle 9.6.0 через Gradle Wrapper, AGP 9.4.1, SDK `platforms;android-37.0`, Build Tools 36.0.0, NDK 28.2.13676358 и Rust 1.95.0. `targetSdk` равен 35. Совместимость с Android 17 проверяется на API 37, а переход на поведение `targetSdk=37` требует отдельной приёмки.

```bash
git clone -b codex/android-flowseal https://github.com/SPStan/tg-ws-proxy-android.git
cd tg-ws-proxy-android
rustup toolchain install 1.95.0 --profile minimal
rustup target add --toolchain 1.95.0 aarch64-linux-android
sdkmanager 'platforms;android-37.0' 'build-tools;36.0.0' 'ndk;28.2.13676358'

cargo +1.95.0 test --locked
bash scripts/build-android-native.sh arm64-v8a
java -classpath gradle/wrapper/gradle-wrapper.jar org.gradle.wrapper.GradleWrapperMain :app:assembleArm64Debug --no-daemon
bash scripts/verify-android-apk.sh app/build/outputs/apk/arm64/debug/app-arm64-debug.apk
```

Проверка APK выводит сертификат подписи, выравнивание APK и сегменты `LOAD` всех упакованных ARM64-библиотек, а также сохраняет SHA-256. JNA загружает упакованный `libtgwsproxy.so` и вызывает его C-экспорты. Сборка включает Rust-исходники текущего коммита.

Для воспроизведения Android-основы используйте [коммит CI исходной сборки](https://github.com/SPStan/tg-ws-proxy-android/commit/f26c3cb), который добавляет только workflow над архивной ревизией. [Результат исходной сборки](https://github.com/SPStan/tg-ws-proxy-android/actions/runs/45088733844). Локально для того checkout установите `platforms;android-35` вместо `platforms;android-37.0` и выполните команды из его workflow.

Для последующих релизов загрузите постоянный ключ владельца в GitHub Actions Secrets. Workflow ожидает `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` и `ANDROID_KEY_PASSWORD`. Запустите Android workflow с параметром `sign_release`. Артефакт `arm64-release` содержит проверенный подписанный APK. Пробный APK подписан отладочным ключом CI. Переход с debug на APK с ключом владельца потребует удаления debug-версии приложения.

Для проверки на эмуляторе CI собирает отдельный APK x86_64 под API 37. По умолчанию используется стандартный образ с размером страницы 4 КБ. Для образа 16 КБ запустите workflow вручную с параметром `emulator_16k`.

## Проверка на телефоне CP3A.261005.005

```bash
adb devices -l
adb shell getprop ro.build.id
adb shell getprop ro.build.version.sdk
adb shell getprop ro.product.cpu.abilist
adb shell getconf PAGE_SIZE
adb logcat -s ProxyService TgWsProxy AndroidRuntime
```

1. Проверьте наличие `arm64-v8a` в ABI, `37` в SDK и `CP3A.261005.005` в номере сборки. Если размер страницы равен 16384, установка и запуск должны проходить без ошибки выравнивания.
2. Установите APK, запустите сервис и проверьте уведомление и строку `Proxy ready: listening on port 1443`. Примените настройки в Telegram, отправьте сообщение в «Избранное» и загрузите ранее не кешированное фото и большой файл.
3. Для проверки CF-прокси очистите список Worker, настройте рабочий CF-домен и подтвердите маршрут в журнале и на сервере. Затем включите Worker, отдельно подтвердите запрос `/apiws?dst=…&dc=…` на его стороне. В обоих случаях проверьте WSS и WS. В WSS сервер должен увидеть TLS и HTTP Upgrade, в WS — сразу HTTP Upgrade. При подсчёте результатов игнорируйте сеансы, переведённые на другой маршрут.
4. С включённым HTTP/2 и TLS проверьте медиа. При успешном выборе HTTP/2 журнал содержит `DC… media -> CF HTTP/2`, а сервер видит `HEAD /api` и `POST /api` с ALPN `h2`. После включения режима WS и перезапуска подтвердите медиа по `/apiws`. При нерабочем CF-домене ожидается явная запись об ошибке и возможный выбор резервного маршрута.
5. Погасите экран на несколько минут, проверьте доставку сообщения и наличие уведомления после разблокировки. Переключитесь с Wi-Fi на мобильную сеть и повторите отправку сообщения и загрузку файла.
6. Остановите сервис, проверьте исчезновение уведомления и возможность нового старта на порту 1443. Запустите приложение после принудительной остановки и подтвердите сохранение настройки TLS.

## Сверка с Flowseal

[Flowseal v1.11.4](https://github.com/Flowseal/tg-ws-proxy/releases/tag/v1.11.4) — `2085861957070eeea07990a522b29f42e5230210`. [Архивная Android main](https://github.com/amurcanov/tg-ws-proxy-android/tree/540e588d15fbdf806f694fbe0b952ff044d39a07) — `540e588d15fbdf806f694fbe0b952ff044d39a07`, на 30 коммитов позже Android v1.2.3 (`1ded446e3e499d56b6ea2b53109a7b0845215d69`).

| Функция Flowseal | Состояние Android-основы | Изменение | Проверка |
| --- | --- | --- | --- |
| DC и медиа | WS-маршрутизация по DC, медиа и тестовым DC | Сохранены прямые WSS и TCP:443. Worker для тестового DC идёт без пула | Rust проверяет выбор транспорта и ограничение повторных TCP-попыток |
| Пул соединений | Пул прямых WSS и Worker | Режим закрепляется за сеансом. Worker повторно заполняет и обновляет пул с задержкой при ошибках | Тест конфигурации двух пулов, smoke-тест перезапуска |
| Список CF-доменов и Worker | Активный CF-домен, балансировщик, список Worker в Rust | Worker настраивается в Android. CF использует явную политику WS/WSS и проверку сертификатов в WSS | Локальные WS/WSS-серверы, проверка протокола на реальном CF по инструкции выше |
| Резервные маршруты | Worker → CF WS → TCP | Worker → CF HTTP/2 для медиа → CF WS → TCP. TCP подключается к 443 с задержкой между сбоями | Тест работы без понижения WSS до WS и проверка TCP backoff |
| HTTP/2 для медиа | Отсутствовал | ALPN `h2`, preflight `HEAD /api`, параллельный `POST /api`, преобразование MTProto-кадров и лимиты буферов | Локальный сервер HTTP/2, тесты MTProto-кадров. Есть ограниченный повтор последнего небольшого зашифрованного пакета. Ротация занятых потоков и полная история повторов Flowseal ещё не перенесены |
| Входящий Fake TLS | Rust поддерживал входящий Fake TLS, Android не настраивал домен | Настройка маскирующего домена, `ee`-ссылка, выбор шифра и группы, профиль размера первого TLS-ответа | Rust проверяет форму и HMAC ответа. Проверка с Telegram на телефоне по инструкции |
| Пользовательские настройки | Compose, DataStore, автостарт, пул, DC, тема и логи | Добавлены списки CF, параметры транспорта, буфер, тестовые DC и PROXY protocol. Обновления проверяются в этом форке | Сборка и эмуляторный сценарий UI |
| Настольная интеграция | Фоновый Android-сервис, уведомление, плитка, переход в Telegram, диагностика | Используются Android-эквиваленты. Системный трей, desktop-инсталляторы и переносимый режим относятся к настольным системам | APK и эмулятор |

На закреплённом исходнике выполнены 136 эталонных тестов по WS, TCP fallback, пулам, HTTP/2 и Fake TLS.

При обновлении проверьте список релизов Flowseal и сохраните полный SHA стабильного тега. Сверьте изменения в `proxy/tg_ws_proxy.py`, `bridge.py`, `pool.py`, `cf_h2.py`, `fake_tls.py` и соответствующих тестах. Обновите таблицу, повторите Rust-тесты, CI и приёмку на устройстве.
